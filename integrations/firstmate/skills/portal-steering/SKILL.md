# portal-steering

This skill changes **where firstmate's messages live**, and nothing else.

Stock firstmate passes messages as files: `bin/fm-send.sh` writes a numbered record
into `state/<id>.inbox/`, and the worker acknowledges it by moving that file into
`handled/`. With this skill installed, the message body and its acknowledgement live
in a firstmate-port portal instead, reached over HTTP by the `fm-steer` CLI. Every
message is then visible on the portal - from a phone, from a second machine, from
anywhere holding a token - instead of only in a directory on the fleet host.

Everything else about firstmate is unchanged: spawning, supervision, status files,
worktrees, briefs, no-mistakes, merges. This is a transport swap, not a new
architecture.

The portal inbox is in memory. A portal restart loses pending and unacked items;
there is no automatic redelivery or restoration.

## Preconditions

- A firstmate-port instance you can reach, and its URL.
- `fm-steer` on PATH: `go build -o ~/.local/bin/fm-steer ./cmd/fm-steer` from a
  firstmate-port checkout (or `./tools/bazel build //:fm-steer`).
- One login on the fleet host: `fm-steer auth login --instance <your portal URL>`.
  That stores a token at `~/.config/fm-steer/credentials.json` (mode 0600), which
  every agent running as that user shares - firstmate and every crewmate it spawns
  need no login of their own. A second mate on a **remote** home is a different user
  on a different machine and needs its own login there.
- The approval step is a human in a browser. Never try to complete a device-code
  login on the captain's behalf.

`export FIRSTMATE_INSTANCE=<your portal URL>` once and `--instance` can be dropped
from every command.

## The channel map

| Message | Stock firstmate | With this skill |
| --- | --- | --- |
| captain → firstmate | `bin/fm-inbox.sh note <text>` | `fm-steer inbox put` (no `--task`; lands under key `firstmate`) |
| firstmate → crewmate | `bin/fm-send.sh <task-id> <text>` | `fm-steer inbox put --task <task-id>` |
| crewmate reads it | list `state/<id>.inbox/*.msg` | `fm-steer inbox next --task <task-id>` |
| crewmate acknowledges | `mv state/<id>.inbox/NNN.msg .../handled/` | `fm-steer inbox ack --ack <token>` |
| crewmate → firstmate | `state/<id>.status` line | unchanged - status files stay on disk |
| captain → liaison → firstmate | same on-disk record | orders under `firstmate`; liaison relays through its parent channel |
| firstmate / liaison → captain | same on-disk record | `fm-steer inbox put --task captain`; only captain reads and acknowledges |

Status files are deliberately not moved. A `state/<id>.status` line is a wake event
that firstmate's watcher reads locally; it is not a message, and routing it through
the network would put a supervision loop behind an HTTP call.

There is **one** portal inbox. Task keys partition it. Do not create a second portal
channel, a per-home inbox, or a mirror queue.

## Steering a crewmate

Send the body on stdin with a quoted heredoc, never with `--body`:

```sh
fm-steer inbox put --task <task-id> <<'FMSTEER'
Two things:
1. rebase on main
2. keep the PR draft
FMSTEER
```

`--body "..."` is wrong for a steer. Steers are routinely multi-line and contain
quotes, backticks and `$`, all of which the shell mangles or expands. The quoted
heredoc sends exactly the text written.

`put` prints the stored item as JSON, including the `ack` token the worker will need.
A non-zero exit means **the steer did not happen**. Do not carry on as though it
landed: report the failed delivery and stop. Never fall back to `bin/fm-send.sh`
or the on-disk inbox for the order.

### Ringing

`fm-steer inbox put` writes to the portal. It does not touch the crewmate's terminal.
Stock `bin/fm-send.sh` did both, so this is the one capability the swap costs.

After every successful crew put, send one constant doorbell line:

```sh
bin/fm-send.sh <task-id> 'portal instruction waiting: fm-steer inbox next --task <task-id>'
```

That record is a doorbell, never the orders. It carries no instruction text, the
crewmate clears it with the stock `handled/` move, and firstmate's re-ring and
stuck-crewmate ladders keep working unchanged.

## Dispatching with a portal brief

`bin/fm-brief.sh` generates a `# Firstmate instruction inbox` section that points at
`state/<id>.inbox/`. That text is generated by a tracked script; do not patch the
script. Replace the section in the scaffolded brief instead - `data/<id>/brief.md` is
home-local and gitignored - after scaffolding and before dispatch.

Replace the whole generated section with:

```markdown
# Firstmate instruction inbox
Firstmate steers you through the firstmate-port portal, not through files on disk.
At any natural checkpoint, and whenever your terminal says a portal instruction is
waiting, run `fm-steer inbox next --task <task-id>`. Exit 1 with no output means
nothing is pending; that is the normal empty case.
When it prints an item, act on its `body`, then acknowledge it with
`fm-steer inbox ack --ack <the item's ack>`. The ack IS the acknowledgement:
without it firstmate rings again and eventually treats you as stuck.
Never ack an item you have not acted on. `fm-steer inbox ack` prints `acked` even
when the portal rejected the token, so confirm with
`fm-steer inbox list --task <task-id>` that the item is gone.
Anything already sitting in a `state/<id>.inbox/` directory is a doorbell, not
orders: clear it with the stock `mv <file> handled/` and take the real instruction
from the portal.
```

Substitute the real task id. Leave the rest of the brief exactly as generated.

## Taking and acknowledging an instruction

```sh
fm-steer inbox next --task <task-id>   # oldest pending item as JSON; exit 1 when empty
fm-steer inbox ack  --ack <token>      # after acting on it
fm-steer inbox list --task <task-id>   # everything pending or delivered-but-unacked
```

`next` marks an item delivered-but-unacked. It stays in `list` until acked, but `next`
will not hand it out twice - so record the `ack` token when you take one, or you
cannot close it.

Always pass `--task` on `next`. Without it the portal hands back the oldest item
across every key, and taking an item is what removes it from the queue: a steer meant
for another task would be consumed here and never delivered there.

`fm-steer inbox ack` prints `acked` and exits 0 even when the portal rejected the
token. Confirm with `inbox list` before believing an ack.

## Completion notices

A bare `fm-steer inbox put` - no `--task` - files under the key `firstmate`. That is a
message *for firstmate itself*, which is how a completion notice, a question, or a
captain's order from a phone reaches the fleet:

```sh
fm-steer inbox put <<'FMSTEER'
fm-port-steer-skill: PR https://github.com/<owner>/<repo>/pull/123 is up, checks green.
FMSTEER
```

Without a liaison, firstmate drains that key with `fm-steer inbox next --task firstmate` when a session
runs and the captain asks. With a liaison, only the liaison drains it and relays
through its parent channel. Captain-facing notices instead use
`fm-steer inbox put --task captain`; only the captain reads and acknowledges that
key. Nothing polls on its own. The portal inbox is not a pager.

## Optional: the portal liaison second mate

Off by default. Enable it only when the captain asks.

A second mate here is an ordinary firstmate second mate - a persistent direct report
with its own isolated `FM_HOME` - given one narrow charter: **carry orders from the
portal to the first mate, and carry completion notices back**. It exists so the portal
channel has an owner that is never mid-turn on fleet work.

**It may:** exclusively drain the `firstmate` key, hand each order to the first mate
through its parent channel, and put completion and status notices under `captain`.
While it is enabled, firstmate does not also drain `firstmate`. Only the captain
reads `captain` with `fm-steer inbox next --task captain` and acknowledges after
reading; the liaison never consumes its own outbound notices.

**It may not:** run the fleet, dispatch or spawn crewmates, take project work, or
merge anything. An order it cannot relay goes back to the captain as a notice; it is
never something it does itself.

### Enable

Your firstmate's own `secondmate-provisioning` skill owns the exact provisioning
sequence and is authoritative if it has drifted. In current firstmate that is:

```sh
FM_SECONDMATE_CHARTER="$(cat "$FM_HOME/data/portal-steering/secondmate-charter.md")" \
  bin/fm-brief.sh portal-liaison --secondmate --no-projects
bin/fm-home-seed.sh portal-liaison - --no-projects
```

then a one-line route in `data/secondmates.md`, and one login for that home if it is
remote. `secondmate-charter.md` next to this file is the charter text to use.

Record the choice in the standing block by re-running the installer with
`--secondmate <id>` so the block says which second mate owns the portal channel;
see "Idempotency" below.

### Retire

```sh
bin/fm-teardown.sh <id>
```

Non-forced teardown refuses while that home has in-flight work; that refusal is
correct, not an obstacle to route around. Never `--force` unless the captain has said
to discard the work. Then re-run the installer with `--no-secondmate` so the standing
block stops claiming a liaison exists.

Retiring the second mate does not turn off portal steering. The two are independent.

## Idempotency

Everything this package installs is either a marker-delimited block or a file it owns
outright, so installing twice is the same as installing once:

- `data/captain.md` gets exactly one block between
  `<!-- BEGIN firstmate-port portal-steering -->` and the matching `END` marker. A
  re-run replaces what is between the markers in place. It never appends a second
  block, and it never touches a line outside them.
- `data/portal-steering/` is owned by the installer, and its files are overwritten by
  name. Install deletes nothing at all; uninstall deletes only the files it wrote and
  leaves anything you added there in place.
- Nothing is written inside firstmate's git checkout outside gitignored `data/`.
  This matters: firstmate's fast-forward self-update skips a home whose checkout is
  dirty, and an untracked file under `.agents/skills/` or `bin/` would count as dirty
  and quietly stop `/updatefirstmate` from ever advancing that home.
- Enabling the second mate is a separate, explicit operator action. The installer only
  records which one owns the channel; it never seeds or tears down a home, so
  re-running it cannot duplicate, orphan, or clobber a second mate.

Change a setting by re-running install with the new flags, not by hand-editing the
block. Hand edits are lost on the next run, which is the point: the markers are what
keep a second copy of a conflicting rule from accumulating in the captain's standing
context.

## Uninstall - back to stock firstmate

```sh
integrations/firstmate/install.sh uninstall --fm-home "$FM_HOME"
```

That removes, and nothing else:

1. the marker block from `$FM_HOME/data/captain.md` - the file is left byte-identical
   outside the markers, and is deleted only if the block was its entire content;
2. `$FM_HOME/data/portal-steering/` - this skill, the charter, and the recorded
   settings. A file you added there is not deleted; the directory is left with it.

Then, by hand:

- Retire the liaison second mate if one was enabled: `bin/fm-teardown.sh <id>`.
- Drop the replaced `# Firstmate instruction inbox` section from any brief of a task
  still in flight, and restore the stock text - the paragraph
  `bin/fm-brief.sh` generates, pointing at `state/<id>.inbox/` with the
  `mv <file> handled/` acknowledgement. New briefs are stock again automatically,
  because the generator was never patched.
- Tell any running crewmate, once, that the portal plane is off and the on-disk inbox
  is live again.
- Optionally `fm-steer auth logout` and remove `~/.config/fm-steer/credentials.json`.
  Leaving the login in place is harmless; nothing reads it unless asked.

Nothing has to be put back for stock operation to resume. `bin/fm-send.sh`,
`bin/fm-inbox.sh`, `state/<id>.inbox/`, and the `handled/` move were never modified,
disabled, or moved - they simply stopped being used while the block was present.
Portal items still sitting unacked stay on the portal; `fm-steer inbox list` shows
them, and they can be drained or ignored.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| `not logged in; run fm-steer auth login` | No credentials file, or it holds no token |
| `{"error":"unauthorized"}` | Token lapsed, or the instance was rebuilt - log in again |
| `{"error":"invalid"}` from `put` | Empty body |
| `inbox next` exits 1 silently | Nothing pending; the normal empty case |
| `acked` but the item is still in `list` | The portal rejected the token; `ack` exits 0 anyway |
| Connection refused | Wrong `--instance`/`FIRSTMATE_INSTANCE`, or the portal is not up |
| A crewmate never picks up a steer | The ring was not sent - it is waiting for its next checkpoint |
| `/updatefirstmate` reports a home skipped as dirty | Something was installed inside the firstmate checkout outside `data/`; move it under `data/` |

Never hand `fm-steer` a NATS URL, NATS credentials, or a token on a command line. It
speaks HTTP to the portal and nothing else; the portal is the only JetStream client.
